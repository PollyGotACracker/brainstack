# 파일 작업

## 착수 절차

이 절차는 파일 작업 응답에 적용한다.

### 착수 조건

- 명확한 작업 지시가 있는 경우 해당 작업에 착수한다.
  지시가 없는 경우 조사와 권고만 제시한다.
- 파일 작업의 필수 요소가 누락된 경우 필수 정보를 질문한다.
  질문에는 누락 항목과 그 정보가 필요한 이유를 적는다.

### 대상과 완료 기준

- 현재 요청의 요구사항과 완료 기준 충족에 필요한 대상을 선정한다.
  각 대상과 요청의 관련성을 확인한다.
- 완료 기준 확정은 사용자가 결정한다.
  사용자가 정한 기준이 없는 경우 사용자가 명시한 요구사항을 기준으로 결정한다.
- 측정 방법이 없는 항목은 완료 기준을 유지하고 `미측정`으로 표시한다.
  해당 항목에 확인 가능한 대안을 제시한다.
  기준의 변경·제외는 사용자 승인 후 반영한다.

### 착수 승인

- 파일 변경 전 아래 형식으로 변경 내용을 제시한다.
  승인이 필요한 변경이면 승인을 받은 뒤 착수한다.
- 변경·삭제 내용은 대상 파일의 실제 원문과 대조한 unified diff로 제시한다.
  요약·비교 표 대신 diff 원문을 제시한다.
- 다른 에이전트의 요청으로 파일을 바꾼 경우 결과 보고에 실제 적용한 diff를 포함한다.

```markdown
## 작업 승인 필요

<변경 내용>

### 작업 대상: <개수>

- `<대상>`
  - 목적: <목적>
  - 범위: <범위>

<생성: 실제 작성되는 구체적 내용을 제시>
<변경·삭제: 실제 원문과 대조한 unified diff>

### 완료 기준

- <기준>
```

## 완료 검증 절차

- 적용 대상은 조건 기반 검색·파일 작업 응답이다.
- 수행 시점은 응답 종료 전이다.

### 판정과 재작업

- 착수 시점의 완료 기준 전부를 실제 결과와 대조한다.
  이미 확인한 결과는 변경·누락이 생긴 범위만 다시 확인한다.
  충족은 `PASS`, 미충족은 `FAIL`, 결과 없음은 `미측정`으로 판정한다.
- `FAIL` 또는 `미측정`이 있는 경우 다음 사항을 우선 확인한다.
  - 승인 범위
  - 재작업 중단 조건
  - 3항의 재작업 횟수
- 계속 가능한 항목은 즉시 재작업한 뒤 재판정한다.
- 2회 재작업 후에도 `FAIL` 또는 `미측정` 기준이 남으면 해당 기준, 원인, 유효한 대안을 제시한다.

### 보고와 회고

- 전 기준이 `PASS`인 경우에만 완료를 보고한다.
  보고에는 기준·실제 결과·판정을 문단 또는 목록으로 제시한다.
  여러 기준을 같은 속성으로 조회하는 데 유용한 경우 아래 표 예시를 사용한다.
- 응답 회고 요청 시 반복된 실수와 다른 대화에도 적용 가능한 개선안을 제시한다.

```markdown
## 완료 보고

완료 보고용 표 예시.

| 기준   | 실제 결과   | 판정                   |
| ------ | ----------- | ---------------------- |
| <기준> | <실제 결과> | <PASS / FAIL / 미측정> |
```

## 파일 작업 원칙

### 로컬 파일 작업

- 파일·폴더 이동은 원본·목적지가 사용자 요청 또는 승인에 포함된 경우에 수행한다.
  Skill 이름 결정의 승인은 이름에 한정한다.
  디렉터리 이동·외부 링크 설치에는 각각 대상·행동·영향 범위의 승인을 적용한다.
  이동 전 활성 참조와 링크의 실제 대상을 확인한다.
  기존 연결에 영향이 있으면 승인된 링크 갱신의 실행 가능 여부와 복구 방법을 확인한 뒤 이동한다.
- 파일을 만들거나 바꿀 때는 같은 종류의 기존 파일 컨벤션을 먼저 확인해 따른다.
  기존 컨벤션이 원칙과 충돌하면 작업 전 알린다.
- 반복 문장을 수정할 때는 절 제목이나 인접한 고유 문장으로 대상을 구분한다.
  수정 후 변경 위치와 참조 대상을 대조한다.
- 지침·주석에서 대상에 구체적인 명칭이 있으면 경로 대신 그 명칭을 쓴다.
- 파일 읽기·검색·수정은 Read·Grep·Glob·Edit·Write 도구로 한다.

### 문서 변경

- 문서 삭제·이동 계획은 원본 절이나 행별 이동 위치를 대조표로 제시한다.
- 문서 변경 전 요청과 기존 문서에서 독자를 확인한다.
  독자에 따라 결과가 달라지고 독자가 미확인이면 사용자에게 질문한다.

## 문서 서식

### 문장 작성

- 짧은 항목은 마침표 없는 명사구, 규칙·설명은 `~한다.`, `~이다.` 완결 문장으로 쓴다.
- 문장마다 핵심 하나만 담는다.
- 문서 작성 과정을 언급하는 메타 표현을 제거한다.
  단, 문서 내용에 해당하는 사용자 요구사항과 제약은 보존한다.
- 문서의 본문·목록·주석은 완결된 문장마다 줄바꿈한다.

### 구조 표현

- 핵심 단어는 굵게, 강조할 단어는 기울임으로 표시한다.
- 본문은 중첩 글머리 기호 목록을 중심으로 작성한다.
  항목 아래 들여쓴 무기호 줄로 보충 설명을 붙인다.
  절차를 기술하는 경우 번호 목록을 사용한다.
- 서술 문단은 도입·전환·결론에만 쓴다.
- 목록 들여쓰기는 탭 1개를 한 단계로 사용한다.
  예외로 YAML 프론트매터는 공백 2개를 사용한다.
- 예시는 `e.g.`, 참고 정보는 `cf.`로 표기하며 뒤에 내용을 한 칸 띄어 작성한다.
- 예시는 그 대상을 명시하고, 길면 언어를 지정한 코드 블록으로 작성한다.
- 소제목은 4어절 이하의 명사구로 작성한다.
- 폴더 구조는 tree 형태로 작성한다.
  - `├──`, `└──`, `│`
- 인물 발언은 인용 블록 마지막 줄에 `— 이름, 소속(직책)`을 붙인다.
- 구성 요소 비교·범위 구분에 표를 쓴다.
  - 머리글은 모두 굵게 한다.
  - 짧은 값 열은 가운데 정렬, 설명 열은 왼쪽 정렬한다.
- 커맨드, 프롬프트, 템플릿은 코드 블록으로 작성한다.
- 전체 흐름은 코드 블록 안에 `→` 또는 `↔`로 이어 쓴다.
- 이미지는 `![설명](파일명.확장자)` 형식이다.
- 링크는 `[표시 이름](URL)` 형식이다.

### 공개 문서

- 외부 공개 문서의 프로젝트 구조·경로는 개인 폴더명을 임의 폴더명으로 대체한다.
